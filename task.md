# weather-table сбор данных о влажности и температуре в квартире

## Контекст и цель

В квартире установлены электронные датчики температуры и влажности от Xiaomi (Mijia) LYWSD03MMC, которые передают измерения по bluetooth:
- `living_room` «Комната» — `A4:C1:38:20:64:92`
- `storage` «Кладовка» — `A4:C1:38:3D:B6:AF`

Рядом стоит мини-сервер HELOR (HL) 192.168.2.2 с BT контроллером на борту. HELOR работает под управлением ОС Ubuntu 24.04.4 LTS (GNU/Linux 7.0.0-30-generic x86_64).

Требуется разработать систему сбора почасовых данных с датчиков, хранения и красивого вывода.

## Журнал исследования

### Шаг 1: анализ бродкаста датчика (стоковая прошивка)

Протокол Xiaomi MiBeacon (UUID 0xFE95), данные зашифрованы AES-CCM — для чтения нужен bindkey.

### Шаг 2: получение ключа из облака Xiaomi

Через [Xiaomi-cloud-tokens-extractor](https://github.com/PiotrMachowski/Xiaomi-cloud-tokens-extractor) получены данные датчика (в `.env`, не публиковать).

### Шаг 3: замена датчика и прошивка на ATC

Первый датчик сломался при замене батареи. Новый датчик перепрошит на **ATC_MiThermometer v5.9 (pvvx)** (протокол Custom, без шифрования, UUID 0x181A). Второй датчик (`storage`) перепрошит так же. Оба рассылают пакеты в формате pvvx custom (проверено 2026-10-10 сканированием эфира: имена `ATC_206492`, `ATC_3DB6AF`).

**Формат ATC Custom (UUID 0x181A):**

```
[0:6]   MAC (6 bytes, в обратном порядке)
[6:8]   temperature (int16 LE, /100)
[8:10]  humidity (uint16 LE, /100)
[10:12] battery mV (uint16 LE)
[12]    battery %
[13]    counter
[14]    flags
```

Пакет приходит примерно раз в 22–25 с (по логам коллектора), несколько одинаковых пакетов с тем же counter — повторы одного измерения. Сигнал: `living_room` около −77…−90 дБм (на пределе), `storage` около −75 дБм.

### Шаг 4: реализация сбора с агрегацией

Алгоритм:
1. Непрерывный BLE-скан (`bleak` `detection_callback`).
2. Dedup по counter — один counter = одно уникальное измерение.
3. Накопление уникальных измерений в окне (на HELOR 180 сек).
4. Свёртка: средние значения температуры, влажности, батареи за окно.
5. Запись одного усреднённого показания в БД с числом измерений (`packets_count`).
6. Сброс окна, старт нового.

### Шаг 5: уличная погода — история провайдеров (2026-09-26 … 2026-10-11)

- Первоначально использовался Open-Meteo; 27.09 проект перешёл на WeatherAPI.com (с circuit-breaker). Причина смены в git не записана, но с HELOR **`api.open-meteo.com:443` не отвечает** (проверено 11.10: соединение не устанавливается, curl ждёт ~130 с). WeatherAPI с HELOR нестабилен (серия таймаутов 10.10, успешные запросы нерегулярны).
- Найдены и исправлены ошибки в приёме погоды: (а) в БД сохранялся весь «сегодняшний» прогноз, включая будущие часы, поэтому «последнее показание» `outdoor` оказывалось в будущем (искажало `/health` и график); (б) проверка «час уже записан» не срабатывала (сравнение «наивных» и «aware» дат), возможны дубли; (в) пустой ответ провайдера не считался сбоем, backoff не включался; (г) блокирующий `requests` вызывался прямо в asyncio-цикле; (д) ключ WeatherAPI попадал в лог.
- Принято решение хранить **только факт**: часы, ещё не наступившие, отбрасываются, запись — upsert по часу.
- Проверены провайдеры с HELOR: MET Norway (отвечает за 0,24 с), wttr.in в компактном формате `%t|%h` (0,17 с); JSON-режим `j1` у wttr.in зависает. Контрольный замер 11.10: Яндекс 13 °C / 55 %, Google 13 °C / 66 %, wttr.in 13 °C / 54 %, MET Norway 11,9 °C / 71,8 %. Основным выбран **wttr.in**, запасные — MET Norway, Open-Meteo, WeatherAPI (если задан ключ).
- Старые исторические строки `outdoor` (записанные как прогноз до 11.10) пока оставлены как есть.

### Известные ограничения

- Датчики рассылают пакет раз в ~22–25 с, и `bleak`/BlueZ отдаёт не все пакеты; при слабом сигнале пропусков больше. Агрегация по окну сглаживает это.
- Открытие `api.open-meteo.com` с HELOR недоступно; Open-Meteo оставлен в коде как запасной.
- MET Norway и wttr.in дают только снимок текущего часа; при пропуске опроса этот час останется пустым.
- Погода — модельные данные (не станция); влажность у разных источников расходится заметно.
- Время в БД хранится в UTC без указания пояса; API отдаёт UTC с суффиксом `Z`.
- Ретеншн отключён по умолчанию (`RETENTION_DAYS=0`).
- Поддерживается только формат рассылки ATC Custom (pvvx, UUID `0x181A`). Код BTHome (парсер, UUID и GATT-чтение) удалён 2026-10-11: он не использовался и не соответствовал спецификации v2. Датчик в `sensors.yaml` с другим `protocol` пропускается с ошибкой в логе. Если понадобится BTHome (например, для Home Assistant), парсер пишется заново по спецификации bthome.io v2: UUID `0xFCD2`, версия в битах 5–7 device info, однобайтовые ID фиксированной длины (`0x00` packet id, `0x01` батарея, `0x02` температура, `0x03` влажность, `0x0C` напряжение).
- Каталог `~/vsuh-helor-conf/services/opt/weather-table` на HELOR — устаревшая копия проекта (коммит `1911cfd`); рабочая копия и источник истины — `/opt/weather-table` и git-репозиторий в vault.
